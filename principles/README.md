# 基础设计原则

每个界面都需要回答四个问题：用户想完成什么，怎样让人读懂，动作会带来什么结果，以及谁有权决定是否执行。先识别正在作哪一种决定，再用相应的原则评审。具体验收方法见[设计要求与验收](../docs/tasks.md)。

| 原则 | 负责什么 | 判断问题 | 规范落点 |
|---|---|---|---|
| 意图优先 | 目标与内容。决定服务谁、保留哪些信息与行动、怎样才算办成 | 用户此刻想做什么？选择下一步前，必须先看见什么？ | [内容](content.md)、[交互](interaction.md)的信息递进 |
| 表达服务判断 | 感知形式。决定怎样用位置、字形、颜色或声音传达已有含义 | 仅凭排版能认出对象、所属分组与可做的动作吗？哪些差异值得突出？ | [视觉](visual.md)、[页面组合](../patterns/page-composition.md) |
| 行为可预期 | 状态转换。决定动作何时生效，如何反馈等待、成功、失败与恢复 | 操作何时生效、影响谁？结果和失败原因看得见吗？ | [交互](interaction.md)、组件与对应模式 |
| 用户有决定权 | 行动权限。决定谁可以发起、改选、撤销、授权或接管 | 改变主意时，用户还能改选、拒绝或接管吗？ | [方案选择与执行授权](../patterns/decision.md)、[自动执行的授权范围](../patterns/write-levels.md) |

分类时，先把一个控件拆成可分别改变的决定。例如查询报表，要保留哪些筛选条件，由意图决定；日期怎样排才便于比较，由表达决定；何时用新结果替换旧结果，由状态转换决定；谁能把结果发给外部收件人，由授权决定。同一页会用到多条原则，每个问题只在负责它的规范里定义一次。

**贯穿每项判断的底线**是信息可信、操作可达。过期数据排得再清楚也会误导，只能用鼠标提交的表单会排除键盘使用者。核对数据来源、时点和业务回执，再用实际输入方式走到结果。[内容原则](content.md) · [无障碍底线](accessibility.md)

## 同一条原则为何会导出不同的设计

一家酒吧可以先让人感受气氛，同时给已有计划的客人保留订位入口。手机上把订位换成订阅，即使新按钮清楚醒目，也让用户更难完成此行的目的。换到查异常的工作台，首屏最值得给的是异常对象、影响与负责人。在两个场景里，首屏的价值都取决于它帮助人作出了什么判断。[酒吧桌面与手机对照](https://www.xiaohongshu.com/discovery/item/6adb6761000000003301ca1b) · [工作台跨端组合](../patterns/page-composition.md#跨端保留任务)

花色繁多的餐具，需要固定名称和价格的位置；外形相近的白盒咖啡，反而需要放大标签差异，再配上可读的名称。Memo Paris 的柠檬黄承担品牌记忆，深咖啡色按钮承担加购。可以把颜色、字形或留白从页面上拿掉再看：若顾客因此认不出品牌或商品，它就有保留的理由；若订单的异常反而更好找，原来的强调就给错了地方。[餐具列表](https://www.xiaohongshu.com/discovery/item/6ad628a9000000002602219a) · [白盒咖啡](https://www.xiaohongshu.com/discovery/item/6ae2ac79000000002c01faaa) · [香水品牌与加购](https://www.xiaohongshu.com/discovery/item/6ad0ed75000000001b022059)

续费开关拨到“关”，顾客会据此判断下个月是否扣费，界面需要兑现这个预期。持续生成的对话则揭示另一件事：即使读者完全理解新消息会把页面带到底部，他也可能想把眼前这一段读完。生成可以继续，何时跳到最新由读者决定。前者关系到对系统的理解，后者关系到系统尊重谁的意愿。[续费设置对照](https://www.xiaohongshu.com/discovery/item/6afc1fa7000000001803a48c) · [持续输出与回读](https://www.xiaohongshu.com/discovery/item/6ada3150000000002c0144b0)

## 把原则用在新页面上

设计时先写一句完整的任务，例如「运营人员查看本周华东的异常，选中上海，把这批明细交给负责人」。这一句话同时给出了入口、比较依据、操作范围和完成标志。用下面的问题评审原型，即使以后更换组件，仍能作同样的判断。

| 设计决定 | 在另一个项目里怎么用 |
|---|---|
| 意图优先 | 写下谁要对哪个对象做什么。从桌面与窄屏分别走到结果。若两个入口优先服务不同意图，说清对应的人与场景。 |
| 表达服务判断 | 在首次看到、还没悬停时，指出分组、可点的对象和操作将影响的范围。换成长短不齐或缺少摘要的记录，再看哪些字段要对齐、哪些差异值得突出。 |
| 行为可预期 | 请人预测“离开后会保留什么、导出会包含哪批对象”。实际执行一次，核对输入、结果、范围和返回位置。 |
| 用户有决定权 | 在确认前改选或退出，核对实际状态仍与用户授权一致。可恢复的操作提供撤销；不可撤回的外部动作在执行前说明对象与范围，请人决定是否继续。 |

任务成本也会改变具体做法。少量本地数据适合即时筛选，耗时查询适合先备齐条件再提交。[整页组合](../patterns/page-composition.md) · [生效时点](interaction.md#操作何时生效) · [结果范围](../patterns/browse.md#已应用的查询范围) · [对话回读](../patterns/page-chat-flow.md#持续输出与回读)

## 冲突时如何决策

先守住真实、可达与授权范围，再看这一刻哪项判断最重要。体验本身也能构成产品价值：初访者靠氛围选店，操作员靠稳定的字段定位异常，审批人有时需要停下来复核。由此决定哪里可以慢、哪里应当快、哪里值得鲜明。个人偏好不足以盖过这些理由。

| 实际冲突 | 决策 |
|---|---|
| 希望自动化节省步骤，同时用户可能要修改方案 | 草稿可以自动准备，选择方案后仍可修改；只有在用户已授权的范围内执行。可撤回的低成本操作直接完成并提供撤销。 |
| 导览说明卡固定，但挡住真实目标 | 目标完整可见优先，说明卡换到可用位置；不截掉高亮来维持卡片位置 |
| 想要透气，但窄窗口装不下表格 | 保留可读字号与操作区域；先重排分栏，必须逐列比较的数据局部滚动，页面外壳不被撑开 |
| 想减少色块，但控件或选中项不可辨 | 保留必要的边界、选中与焦点；移除重复对号、重复标签和无意义底色 |
| 想让页面更短，但读者要靠这些入口选择下一步 | 目录、候选项与影响决定的条件直接可见，先用标题、对齐和留白分组。读者看完摘要就能继续、只有部分人需要追问时，再收起明细。例如异常与负责人直接显示，排查经过可按需展开。 |
| 想让页面饱满，但内容很少 | 收窄阅读范围、聚合相关内容；不扩大卡片或复制指标来填空，不给独立对象强加相同高度 |
| 多件独立事项都需要决定 | 每件事项内部一个主动作；通过分组与任务先后控制整页负担，不机械规定整屏只有一个按钮 |

## 验证与回补

先验证组件的状态与操作，再把组件放回真实页面：同时看顶部与长页下半部、展开内容、加载／空／失败、不同数据长度、窄窗口和对话打开时的布局。组件均合规仍不协调，通常缺的是组合约定；先在页面证明解法，再把跨页面复用的部分补入模板或模式。产品独有流程留在产品中。

验收时写下观察到的结果。例如「查询失败后仍能导出上一批上海明细」能说明范围保持一致。「用户知道会导出哪批」还需要请用户在导出前说出预测，再与文件核对。

这些原则可以修订。先找一个已有原则看似都满足、用户仍会受损的案例，再看新表述能否改变另一个场景的设计决定。单个菜单的高度、某种按钮的色值等具体经验，保留在相应组件或模式里。[如何贡献案例](../CONTRIBUTING.md#从一个案例改进系统)
